# Code flow

## Entry points
- `run.py:main` — CLI. `order "<request>" [--conversation KEY] [--db PATH]` runs one request and stores it; `edit <order_id> "<text>"` patches a stored version (Phase 6, see "Edits" below); `orders show <id>` / `orders list` print the order store; `calibrate` records a cast weight; `packs` lists domain packs; `rates refresh|show|set` runs the gold-rate job once (or every N h with `--every-h`), prints the stored rates with their status, or lets the owner set a rate by hand (see "Gold rate" below).
- `probe/server.py:main` (`python -m probe`) — Phase 6.5 Nonilion probe, a stdlib `ThreadingHTTPServer`. Routes (each also without `/v1`, or under `/<agent>/v1` with agent `[a-z0-9_-]{1,32}`, else 404): `GET /` health (no key), `GET /v1/models`, `GET /v1/models/karigar-probe`, `POST /v1/chat/completions` (JSON or SSE stream), `GET /probe/log?n=` (key), `GET /probe/image.png` (no key, 1 px PNG for the Markdown image test). Per request (`Handler._route`): split path into prefix/agent/route → auth check (`Authorization: Bearer PROBE_API_KEY`) → body: unauthenticated = never parsed (≤ 64 KB drained, else connection closed; only `body_bytes` logged); authenticated = > 8 MB 413, `_parse_json` pre-scan (≤ 100k nodes, depth ≤ 64) then `json.loads`, then `scrub()` → one `request` entry written to `PROBE_LOG` (ASCII JSONL, secrets redacted in path/query/headers/keys/values, data: URIs as type+length, strings > 2000 chars cut, lines ≤ 64 KB, rotated at 10 MB keeping `.1`–`.5`) → route (401 if no key). Any exception in a handler → one-line `error`/`timeout`/`disconnected` log event + OpenAI-style 500/408 JSON (`Handler._fail`). `ProbeServer` caps connections (64 → 503); sockets time out after 30 s; delayed/streaming chat replies are capped at 8 at once (429). Chat replies describe what was received; `probe delay N` / `probe stream N` in the last user message override `PROBE_DELAY_S` / `PROBE_STREAM_LINES`. After a chat reply a `done` event (elapsed_s) or, if the client hung up, a `disconnected` event is logged. Not connected to `karigar/`.
- `python -m karigar.service` / `run.py serve` — Phase 7 service (Render), `karigar/service/http.py:make_server` over `KarigarService`. See "Service (Phase 7)" below.
- `run.py worker` — Phase 7 Blender worker (laptop/WSL), `karigar/service/worker.py:main`: polls the service, runs the Orchestrator, uploads results.
- `run.py ask "<text>" [--conversation K]` — CLI adapter: one message through `KarigarService` with an in-process worker (`LocalClient`), prints the chat reply.

## Request / data flow (`order`)
1. `run.py` imports the packs (`karigar/packs/jewellery`, `karigar/packs/hardware`), which register themselves in `core/registry.py`.
2. `core/orchestrator.py:Orchestrator.handle` returns `core/result.py:JobResult(...).model_dump()` and runs the five agents through the `Transport`:
   1. **Sakhi (intake)** → `pack.intake(text, attachments, sender=...)` (`core/registry.py:Intake`; `sender` is the chat identity passed to `Orchestrator.handle(..., sender=)`, `run.py order --sender`). Jewellery (`packs/jewellery/__init__.py:JewelleryPack.intake`):
      - gold-rate message ("aaj ka rate 22K 14730", no piece word) → `rates.py:parse_rate_message` → `RateMessage {rates, bad}`, or None (no rate word, a question — "?", kya, kitna, what, how… — or only weights after the karats, e.g. "rate of 22k gold 10 grams": falls through to the brief) → `rates.may_set_rate(sender)` (sender must be in `KARIGAR_RATE_SETTERS`, env or `.env`) → else `needs_info`, topic `rate_permission`, nothing saved (the rate card applies) → any `bad` token (not a rupee amount: ≤ 2 decimals, ₹1 to 7 integer digits, strict comma grouping; or the same karat twice with different values) → `needs_info`, topic `rate`, nothing saved → `GoldRateStore.set` (`data/gold_rates.json`, ISO timestamp, `source: "chat"` — the same store RateSource reads; exclusive lock on `gold_rates.json.lock`, atomic temp-file + `os.replace` write; a damaged file is moved to `gold_rates.json.corrupt-<time>` and only valid entries are kept) → `rate_set` reply. No order folder.
      - else `brief.py:analyse`: `core/lang.py:detect` (en / hinglish) → out-of-scope piece (necklace/mangalsutra, anklet, maang tikka; Phase 2.5 brought chain, coin, earring, nosepin into scope) → `out_of_scope` + nearest piece; else draft = LLM JSON validated against `BriefDraft` (one repair call with the validation error) or `_regex_parse` → blocking fields missing (piece, target, ring/bangle size, chain length 16–24 in, karat, old karat) → `needs_info` with up to 3 questions in one reply; else a `Brief` (`family` set by code from style words via `brief.py:family_from_text`, never by the LLM) (`ring_size` → inner diameter via `sizes.py` + `data/ring_sizes.json`). A Brief then needs a usable gold rate: `rates.rate_source().problem(karats_needed(karat, old_gold))` (piece karat, + 24K for old gold); missing / > 24 h old / future-dated / outside the sane range → `needs_info`, topic `gold_rate`, reply from `RateProblem.reply` (says what is wrong, asks for today's rate, never estimates). `BriefDraft`/`Brief` refuse inf/NaN numbers, and `style` keeps only tags from `schema.py:STYLE_WORDS` (anything else is dropped before it can reach a reply). Every reply string comes from `messages.py` in the request's language.
      Non-brief intakes end the order there (nothing stored). Otherwise `out/ORD-<YYYYmmdd-HHMMSS>-<4 hex>/` is created (`OrderStore.new_order_id`) and Sakhi states the brief summary.
   2. **Jauhari (plan)** → `JewelleryPack.plan` → `pricing.py:plan`. A weight/exchange target under the piece's minimum (`detail.min_weight_g`) is refined by `JewelleryPack._below_minimum` (Phase 3, Hero D): every deterministic variant (`designer.deterministic`, no LLM) carrying the customer's stone is built at the low end of its castable range, so `best_achievable` is the minimum *achievable* finished weight, with options "that weight with the stone" and "a smaller stone (`STONE_LADDER`) at its weight". `plan.detail["tolerance"]` = `core/gold.tolerance()` (config default; the orchestrator may replace it with `CalibrationStore.tolerance(workshop)`). Budget mode with a stone but no carat → `detail.joint_stone` (see build). Reads the gold rate once through `rates.RateSource.get_many` (stored in `plan.detail["gold_rate"]` with `per_g`, `set_at`, `source`; a RateProblem → Plan ok=False) and the shop numbers from `data/rate_card.json`, loss % from `core/calibration.py` (the `CalibrationStore` passed as `Orchestrator(calibration=...)`, default `data/calibration.json`). Turns old gold / target weight / budget into a modelled-gram target using `core/gold.py` (old gold credited at its stated karat's purity only; claimed/tested purity is dropped at `BriefDraft`/`OldGold`). An impossible request ends with `infeasible`: `explanation` plus `infeasible {binding_constraint, best_achievable, alternatives ≥ 2}` from `Plan`.
   3. **Naqqash (design)** → `designer.py:propose`. If `designer.family_for(brief)` finds a registered catalogue family (named in the brief, or the first one for chain/coin/earring/nosepin) → `family_variants`: the family's `default_spec` × `variant_axes` multipliers for lighter/balanced/statement, brief owns karat/metal/size/length (no LLM). A new piece type with no family → `designer.NoFamily`. Otherwise (ring/bangle/pendant, no family) LLM variants validated against `schema.py:DesignSpec`; invalid ones are replaced with deterministic fallbacks.
   4. **Karigar (build)** → `JewelleryPack.solve`. Coin: `params.stamp_g` set to the plan's finished weight (the designer stamps the brief's target, default 10 g). `dfm.py:scale_bounds` gives the castable scale range (a family's own `scale_bounds` when registered with one; sourced minimums from `data/casting.json` `dfm_min_mm`); lo > hi → `stone_too_big` (best achievable = largest stone, `dfm.max_stone_d`, in ct). `core/solver.py:solve_monotone` finds the scale where `geometry.py:gold_volume` (metal volume after the stone seats are cut, cached by `spec_hash`) × `gold.density(karat)` (from `data/casting.json`) hits the target within the tighter of 0.1 g / 2%, at most `MAX_ITER` + 2 builds. A miss fills `Solved` via `solve_failure(r, loss, spec)` (binding rule named by `dfm.binding_rule`); if every variant misses, the closest miss binds and alternatives are pooled. Budget with `joint_stone` → `_solve_budget`: one scale grows band and stone together (gem_d = d0 × s) until `pricing.quote` total lands just under the budget.
      **Mesh check (Phase 4)**: `JewelleryPack.solve` = `_solve_core` (all of the above) → `meshdfm.check_spec(spec, scale)` (build at the solved scale, ray-cast thickness per part: `ring_shank`, `prong`, `setting`, `wall`, plus `soft_gold_claws`; rules from `data/dfm_rules.json`; cached by spec hash) → pass → `Solved.warnings` / `mesh_checks` / `issues` (`with_mesh`). Fail or a builder exception → `meshdfm.relax` (family `relax` hook, else width/size × 0.85, fewer petals/beads) → `_solve_core` once more to the same target → check again → pass (warning "retried once with …") or `mesh_refusal` (infeasible, `binding_constraint` "mesh check: <part> at <location>: x mm < min mm"). Edits: `apply_edit` checks after `edits.resolve`, no retry.
      **Weight path** (every builder and family alike): `geometry.build` → builder → `cut_seats` (gold minus the stones' solids, MANIFOLD boolean; retried with micron nudges/turns/growth until `mesh_check` passes, incl. the earring mirror copy; if none passes the uncut clean body is kept with `seats_in_model=False`, the job card warns, and the weight is still the cut volume) → earring `make_pair` (volume × 2).
   5. **Chitrakar (render)** → `JewelleryPack.deliver`: `geometry.build` (dispatches on `spec.family` to `families.FAMILIES[...].builder`, else the original `BUILDERS[piece_type]`; earrings with `pair` get a mirrored copy in `Built.mirror` and doubled volume; the STL is one earring, `job_card.pieces_to_cast` = 2), `render.export_stl` (scaled by `rate_card.json` `casting_shrinkage_pct`, 1% → ×1.01, via the exporter's `global_scale`), `render.export_glb` (unscaled), `render.render_views`, plus `job_card.json` (`jewellery.job_card`: casting weight, expected finished ± tolerance, expected loss, tolerance source) and `job_card.md` (`jobcard.py:job_card_md`: renders, dimensions, size, purity, weights, stones, finishing notes, HUID reminder, rule warnings, "Manufacturability (measured on the mesh)" from `mesh_checks`; `deliver` runs `meshdfm.check_built` on the built gold when the `Solved` carries no results).
   6. **Jauhari (quote)** (Phase 7 order: every solved design is quoted and stored as a version *before* rendering — `on_stage("solved", JobResult without files)` — then 5. delivers each and adds its outputs; a delivery exception sets the order `failed`, keeps the versions, and re-raises) → `pricing.py:quote` → `quote.json` (with `weights` = `pricing.weights`: casting_g, finished_g, expected_loss_g/pct, tolerance_g/pct, and `weight_text` "7.60 g ± 0.30 g finished (cast …)", also in the summary; `JewelleryPack.weights` returns the same dict): lines `{key, label, amount_inr, source, assumed}` for gold (plan's rate + timestamp), making 3.5%, stones ("stone size assumed" when no size was named), hallmarking ₹75/article, GST 3% gold+stones, GST 5% making, and old-gold credit (weight × purity × 24K rate − 2%); whole rupees half-up, total = sum of lines.
3. `order.json` summarises the order. `ConsoleTransport` prints every message.
4. **Order store** (`core/orders.py:OrderStore`, Phase 6): after the plan, the order (request, brief, `asdict(plan)`, lang, status done/infeasible, optional `conversation` key) is written; each solved variant becomes version 1..n with spec, scale, modelled/finished/target g, quote and every output path (`stl`, `glb`, renders, `job_card*`, `quote`; `order_json` on v1). `JobResult.results[i].version` carries the number. File: `Orchestrator(store=)`, else `$KARIGAR_ORDERS_DB`, else `data/orders.sqlite3`.

**Stage hook + logs (Phase 7)**: `Orchestrator(on_stage=fn)`; `_stage` writes one JSON line per stage to the `karigar.stage` logger (`core/stagelog.py`: `{"ts","event":"stage","stage","order_id","ms",…}`, short scalars only) and calls `fn(stage, data)`: intake, plan, design, solve, solved (data = JobResult with spec/weights/quotes, no files), deliver, done (data = final JobResult); `deliver_failed` on an exception. After each ok plan: `plan.detail["tolerance"] = calib.tolerance(workshop)`; result weights = `pack.weights(r, plan)` (Phase 3).

## Edits (`edit`, Phase 6)
`run.py edit <order_id> "<text>"` → `Orchestrator.handle_edit(order_id, text)`:
1. `OrderStore.get` (unknown id → `needs_info`, topic `order_id`).
2. `pack.parse_edit` → `packs/jewellery/edits.py:understand`: regex rules (English + Hinglish) per clause → `EditRequest {pick first|middle|last, changes [Change(field ∈ EDITABLE, op add|mul, amount)], weight WeightChange}`. Only if the rules find no change and an LLM is configured: `parse_llm` (JSON validated by `_LLMEdit`, targets/directions/step words only; a number is kept only if it is written in the text). Nothing understood → `needs_info` topic `edit` with examples.
3. Base version: the picked original variant (versions with no parent) → else `orders.chosen_version` → else the only version → else `needs_info` topic `variant`. A pick with no change only sets `chosen_version`.
4. Fresh `pack.plan(brief, loss)` (today's rate via RateSource). `JewelleryPack.apply_edit` → `edits.apply` (each change applied to the *finished* value = field × scale^power; `EditRefused` → `needs_info` with the reason) → weight edit: `edits.retarget` moves the plan's target from the base version's finished weight → `edits.resolve`: `solve_monotone` on the patched spec where every changed dimension is held at its finished value (`at_scale`: field = finished / s^power), so the scale moves only the rest of the piece (the band); casting rules rechecked at the solved scale (`dfm.scale_bounds`), `dfm.check` rerun. Miss → `infeasible` (contract as for orders).
5. `N = OrderStore.reserve_version` (allocated in a `BEGIN IMMEDIATE` transaction, `version_seq` table, so concurrent edits never share N), `edit_report`, `on_stage("solved")`, then `pack.deliver` into `out/<order_id>/v<N>/`,  (both versions priced with `pricing.quote` under the same fresh plan) → `quote.json` + `edit.json` (`changed`, `resolved`, `weight_g {from,to,delta}`, `price_inr {from,to,delta}`, `to_pay_inr` for exchanges, `spec_diff`, `summary`). Stored as version N (`parent`, `edit_text`, `patch` = spec diff, outputs) and chosen. `JobResult.edit` carries the report.

## Service (Phase 7)
Two processes: the **service** (Render; stdlib only: `karigar/service/{http,core,jobs,convo,replies}.py`) and the **worker** (laptop WSL; `karigar/service/worker.py` + the whole engine). The worker only makes outgoing calls; there is no tunnel.
- **HTTP** (`http.py:make_server`, probe hardening reused from `probe/server.py`): the path decides the credential before any body byte is read — `/`, `/files/…`, `/console/…` none; `/worker/…` `KARIGAR_WORKER_TOKEN`; `/api/…` `KARIGAR_API_KEY` or `KARIGAR_OWNER_TOKEN`; everything else `KARIGAR_API_KEY`. Base paths `/v1`, `/sakhi/v1`, `/karigar/v1` (other agent slugs 404). `GET <p>/models`, `POST <p>/chat/completions` (`validate_chat`: messages list with known roles, string/list content; `tools`, `tool_choice`, `metadata`, … ignored).
- **Chat** → `KarigarService.chat(messages, agent)`: `convo.ref_in_history` (our `_ref K-…_` footer) or `_first_key` (sha256 system + first user message, salted if first seen > 120 s ago) → `continue_conversation(key, last user text, idem = key:#user msgs:hash(last))`: a known idem → the same job (retry); else if the conversation's latest job is running or not fully shown → this message fetches it; else a new `continue` job: payload `order_id` (conversation has a done order) or `pending_text` (latest result was needs_info) + `request_text`. Job + message row are written in one transaction (`jobs.py:JobStore.enqueue`).
- **Wait** (`KarigarService.wait`, ≤ 50 s): polls the job; streams friendly stage lines (`core.friendly`, stage names only) and a heartbeat every 15 s; worker offline (no poll for 90 s) → answers in ~5 s. Reply (`replies.render`, code only): done → per version weight ± tolerance, cast weight, total (₹, Indian grouping), file links; solved → the same numbers + "still rendering, send any message"; failed → numbers if solved, else "send it again"; still running → "Still working (last step …), send any message"; footer `_ref K-…_`. `delivered` 0/1/2 records what was shown.
- **Worker** (`Worker.run_forever`): `GET /worker/jobs` (claims the oldest queued job, lease 300 s; heartbeat) → `ProgressTransport` posts say/progress lines (≤ 1/s) → `make_orchestrator` (real pack, `KARIGAR_WORKER_QUALITY`, `KARIGAR_WORKSHOP`) → `handle_edit(order_id, text)` (needs_info topic edit → try `handle(text)` as a new order) or `handle(request_text, conversation=key)` → at stage "solved" `POST …/solved` → files (render*, stl, glb, job_card(_md), quote, edit; ≤ 25 MB) `POST …/files?name=v<N>-<file>` → paths replaced by `/files/<token>/<name>` → `POST …/result`; an exception → `POST …/fail`. Service down → exponential back-off (≤ 60 s).
- **Reaper** (`JobStore.reap`, on every request/claim/wait): running past lease with attempts left → re-claimable; past the last attempt → failed (`worker_lost`); solved with no update for 900 s → done with the numbers only (`renders_timeout`).
- **JSON API**: `POST /api/orders {text, conversation?, agent?, wait_s?}`, `POST /api/conversations/<key>/messages`, `POST /api/orders/<id>/edits`, `GET /api/jobs/<id>`, `GET /api/orders/<id>/quote`; `Idempotency-Key` header.
- **Files**: `GET /files/<token>/<name>` (token 192-bit from `secrets.token_urlsafe(24)`, name must match). Stored under `<KARIGAR_SERVICE_DIR>/files/<job>/`.

## Gold rate (`rates`)
- Store: `data/gold_rates.json` (`rates.GoldRateStore`; locked, atomic writes). Writers: `ratejob.refresh` (`run.py rates refresh`), `run.py rates set` (owner, range-checked, `source: manual`), chat from a `KARIGAR_RATE_SETTERS` sender. Reader: `rates.RateSource` only (rules in `rate_card.json` → `gold_rate`).
- `ratejob.refresh(fetcher=fetch)`: `fetch(url)` (https only, urllib, 20 s, ≤ 3 MB) → `parse_et_mcx` (html.parser: `<div id="MCX">` → first `span.commodityPrice`, unit span must be "Per 10 GRMS") → `rates_from_mcx` ((MCX + 5,000)/10 for 24K, × karat factor) → sane-range check → `GoldRateStore.set(..., source="mcx-job: …")`. Any failure writes nothing and reports the last rate kept. `run_every(hours)` loops for the worker (6 h).

## Request / data flow (`calibrate`)
`CalibrationStore.record` appends `{designed_g, actual_g}` to `data/calibration.json`; loss % = mean of the last 20 records; `tolerance(workshop)` = 2σ of those losses once ≥ 3 are recorded (floor 0.5%), else the configured default ±4% (`data/casting.json` `tolerance`).

## Owner console (2026-11-14)

`/console/` serves the local UI and vendored fonts/viewer; its shell contains no private data. Distinct owner-token authentication protects `/api/console`, `/api/console/actions`, `/api/console/chat`, and `/api/console/jobs/<id>/seen`.

`console.snapshot` aggregates uploaded worker results and every version into the read model. Counter questions can be acknowledged as displayed before the next answer is enqueued; pending conversation rows merge into the completed order. Shop/catalogue/refresh/calibration actions enter the same queue as `kind=owner`; `service/shop.py` executes them only on the worker. All catalogue geometry, weights and order prompts are supplied by code on that worker. No Blender or pricing dependency was added to the thin service.

Worker progress refreshes online status, and a30second background heartbeat preserves leases through blocking renders. Browser polling ignores unchanged data and preserves fields, open disclosures, and camera/rotation state when content changes.

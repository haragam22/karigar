## 2026-11-11 — The LLM writes specs, code writes numbers (existing)
- **Context**: Whole pipeline.
- **Decision**: The LLM only produces `Brief` / `DesignSpec` JSON validated by Pydantic. Geometry, weights, rules and prices come from deterministic code and data.
- **Why**: Spec "Why it is more than a chatbot"; prices and weights must be traceable.
- **Alternatives**: LLM-generated geometry or prices. Rejected: not checkable.

## 2026-11-11 — Every LLM call has a deterministic fallback (existing)
- **Context**: `core/llm.py`, `brief.py`, `designer.py`.
- **Decision**: No API key or any LLM failure → regex brief parser and fixed design variants.
- **Why**: The demo must never depend on the network.
- **Alternatives**: Hard dependency on the LLM. Rejected for demo risk.

## 2026-11-11 — One monotone scale knob per design (existing)
- **Context**: `core/solver.py`.
- **Decision**: The solver scales the cross-section (ring size fixed) and interpolates in log-log space between castable bounds.
- **Why**: Volume grows monotonically with scale; converges in 4–5 builds. Spec allows bisection for one monotone parameter.
- **Alternatives**: Multi-parameter bounded search (scipy). Deferred until a family needs it (budget mode, Phase 3).

## 2026-11-11 — Blender MCP: dev tool now, constrained drawer agent later
- **Context**: User wants a Blender MCP so work happens in Blender, and later a group of agents that decide a design plus one agent whose only job is to draw in Blender.
- **Decision**: Two stages. (1) Now: a Blender MCP server connected to Claude Code as a dev tool to watch builds, inspect meshes and debug renders. The product pipeline stays headless `bpy`. (2) Later: a drawer agent that may only call Karigar's own parametric builder ops (exposed as MCP tools, e.g. add band / head / motif with typed parameters), never arbitrary Blender Python. Every call is logged into the spec as an op list, so replaying the ops rebuilds the same mesh. Volume, weight, rule checks and pricing stay in code.
- **Why**: Keeps the spec's "LLM never draws a number" guarantee and determinism (same spec → same mesh) while giving the agent a real drawing role. Arbitrary code execution through MCP would be unreproducible and a security hole.
- **Alternatives**: Agent sends raw `bpy` code through MCP. Rejected: not deterministic, not checkable, injection risk. No MCP at all. Rejected: user wants it.

## 2026-11-11 — LLM provider: AgentRouter through the Claude Code CLI
- **Context**: User picked AgentRouter as the API provider. Lessons carried over from hackerrank-orchestrate-october26 (its docs/decisions.md, 2026-10-25), measured there:
  - Direct HTTP to AgentRouter → `401 unauthorized client detected`; only approved coding clients work. Running the official `claude -p` headless is supported. Spoofing client headers was rejected (bypasses provider access control, ban risk).
  - Native function tools fail intermittently (≈ 25% success) → `--tools ""` and our own JSON output instead.
  - Replacing the system prompt → `400 content-blocked`; `--append-system-prompt` works. Very short meaningless prompts were also `content-blocked`.
  - Models then: Claude models and deepseek-v4-flash → 503; gpt-6-astra / gpt-5.6-sol → 400; **gpt-6.1-sol** worked. $1 / $5 per 1M tokens in/out.
  - Latency 9 s typical, but **up to 20 min** per call observed.
  - CLI is single-shot: history is flattened into one prompt; prompt goes over stdin (key never in argv).
- **Decision**: `karigar/core/llm.py` backend `agentrouter` runs `claude -p --bare --disable-slash-commands --strict-mcp-config --tools "" --model $KARIGAR_MODEL --output-format json --max-turns 1 --append-system-prompt <system>` with `ANTHROPIC_BASE_URL=https://agentrouter.org`, `ANTHROPIC_AUTH_TOKEN=$AGENTROUTER_API_KEY`, `ANTHROPIC_API_KEY=""`, `MAX_THINKING_TOKENS=0`. Hard timeout `KARIGAR_LLM_TIMEOUT_S` (45 s); any failure returns None and the deterministic path answers. Key redacted from every log line. An `anthropic` SDK backend stays for migration. Config in git-ignored `.env` (`.env.example` lists keys).
- **Why**: The LLM only shapes briefs and design variants; with 20-minute worst-case latency it must never block a reply, and the demo must run offline.
- **Consequences**: LLM calls run in the worker, never in a chat request handler (Phase 7). The Render worker image needs Node + the `claude` CLI next to bpy. Vision (photo-to-spec, critic) through this CLI is unproven: P1, test before relying on it.
- **Measured here 2026-11-11**: live call from WSL (claude CLI 2.1.276), `gpt-6.1-sol`, Hinglish brief → valid JSON in 13.6 s. Key copied from hackerrank-orchestrate-october26's `.env` at the user's request.
- **No Anthropic key needed** (user has none): the `claude` CLI is only the approved client program; it authenticates to AgentRouter with the AgentRouter key (passed in the CLI's `ANTHROPIC_AUTH_TOKEN` variable) and AgentRouter serves the model. The `anthropic` backend is an unused option for a future provider move; `auto` never picks it without an `ANTHROPIC_API_KEY`.
- **Alternatives (provider)**: OpenAI-compatible HTTP to AgentRouter (blocked, 401). Anthropic API directly (kept as backend; needs a separate key). Local Ollama fallback (used last time; CPU-only and slow, not needed because the deterministic fallback exists here).

## 2026-11-11 — Nonilion probe: stdlib server, log first, safe by default (Phase 6.5)
- **Decision**: `probe/` is a standard-library `ThreadingHTTPServer` (no new dependency), started with `python -m probe` on a Render free web service. Every request (including failed auth and 404s) is logged before routing, so "Test the key" is visible even if it calls an unexpected path. Header names containing authorization/key/token/cookie/secret/password are redacted (body keys too, except `*tokens` like `max_tokens`); the API key value is replaced anywhere in logged strings; data: URIs are logged as `{data_uri: mime, length}`; strings > 2000 chars are cut; the log rotates to `.1` past 20 MB; bodies > 25 MB get 413. `GET /` (health) and `GET /probe/image.png` need no key; everything else does. Delay/stream directives are capped at 900 s / 200 lines. Chat replies include a Markdown table and an image link to `/probe/image.png` to test rendering; a `disconnected` event with elapsed time measures Nonilion's timeout.
- **Why**: Phase 6.5 needs answers, not a framework; logging before auth catches whatever Nonilion sends; caps keep a public endpoint from filling the free-plan disk or holding threads forever.
- **Alternatives**: FastAPI/uvicorn (new dependency, not needed for a probe); request-bin services (third party sees the key and chat).

## 2026-11-11 — Nonilion probe hardening: auth before parse, hard limits, agent base paths (Phase 6.5, security round)
- **Context**: security-breaker findings F1–F8 in docs/security/6.5.md (unauthenticated 24 MB body → 1.2 GB RSS; log blow-up; crashes on hostile JSON; secrets in path/query/keys; no timeouts) and the phase-reviewer gap (two agents need two base URLs). Supersedes the "every request logged before auth" and size numbers of the entry above; the rest of it stands.
- **Decision**: (1) Auth is checked first. Unauthenticated requests are logged as a summary (method, path, redacted headers/query, `body_bytes` from Content-Length, `body: null`); their body is never parsed — up to 64 KB is read and discarded, bigger closes the connection. (2) Authenticated bodies: > 8 MB → 413 without reading; a regex/count pre-scan rejects JSON with > 100,000 nodes (containers + commas) or depth > 64 with 400 `json_too_complex` before `json.loads`; any other parse failure → 400 `invalid_json`. `scrub()` is depth-capped (`[too deep]`). (3) Log: ASCII-only JSONL (`ensure_ascii=True`), each line ≤ 64 KB (else a `{truncated, original_bytes, head}` summary), rotation at 10 MB keeping 5 old files (`.1` newest), `tail()` seeks from the end across files and splits on newline only (so U+2028/U+2029/\x85 cannot hide entries). (4) Redaction: secret words now auth/key/token/cookie/secret/password/passwd/pwd/credential/bearer, exempt only `max_tokens`/`max_completion_tokens`/`max_output_tokens`; a secret-named key redacts its whole value (containers too); the API key (raw and URL-encoded) is replaced in path, query, header names/values, dict keys and string values; query params with secret names are redacted; header values like `Bearer|Basic|Token <x>` are redacted. (5) Socket timeout 30 s (`Handler.timeout`) plus a 30 s deadline on the body read → 408; at most 8 concurrent delayed/streaming replies (429 `too_many_slow_requests`); at most 64 connections (503 and close). (6) A catch-all in the handler logs one line (`error`, `timeout` or `disconnected` event, key redacted, no traceback) and returns OpenAI-style 500/408 JSON; the server's `handle_error` also logs one line instead of printing a traceback. (7) `parse_directives` only accepts numbers of ≤ 6 digits (+ ≤ 3 decimals); fields of the wrong type are tolerated in `describe()`/`_chat`. (8) `client_ip` is the LAST X-Forwarded-For hop (Render appends the real one); the raw header is logged as `forwarded_for`. (9) Base paths: none, `/v1`, or `/<agent>/v1` with agent `[a-z0-9_-]{1,32}` (else 404); the agent is logged (`agent`) and echoed in the reply (line `- agent: sakhi`).
- **Why**: Render free is 512 MB RAM and a public URL; an unauthenticated client must cost almost nothing. Limits are far above any real chat request (a few KB of JSON; photos as data URIs are the only large field). Agent paths let two Nonilion agents import the same probe and be told apart.
- **Alternatives**: a streaming/iterative JSON parser (more code, still stdlib — the pre-scan is enough at 8 MB); `resource`-based memory limits (Linux-only, kills the process instead of refusing the request); a reverse proxy for timeouts/rate limits (another moving part on a throwaway probe); keeping log-before-auth with a smaller cap (still lets anyone fill the log).

- **Out of scope**: this applies only when no ring/bangle/pendant word is present. Chain/necklace words are ignored when old-gold words are present (they are the gold source). Nearest piece: earrings / necklace / chain / maang tikka → pendant, anklet → bangle, nose pin → ring.
- **Language**: `core/lang.py` detects Hinglish from romanised-Hindi word lists (deterministic). `Brief.lang` / `JobResult.lang` is "en" or "hinglish". All Phase 1 replies have both templates (`packs/jewellery/messages.py`).
- **JobResult** (`core/result.py`, Pydantic): status done | infeasible | needs_info | rate_set | out_of_scope. The older keys (`status`, `order_id`, `question`, `explanation`, `results`, `brief`, `plan`) are kept. Infeasible results carry `{binding_constraint, best_achievable {value, unit}, alternatives (min 2)}`. `Plan` and `Solved` carry the same three fields. When every variant fails, the closest miss (|value − target|) supplies the binding rule and best result, and the alternatives are pooled. Each variant reports `weights {modelled_g, finished_g}`.
- **LLM repair**: LLM JSON is validated against `BriefDraft` (stated fields only, all optional). On failure the LLM is called once more with the error appended ("Fix this JSON"), then the regex parser takes over. The LLM's own "question" key is no longer used: questions come from code templates. `designer.propose` is unchanged because it already drops invalid variants and tops up with deterministic ones.
- **Alternatives**: rates handled in the orchestrator (would put jewellery logic in core). A separate result type per status (more surface, no gain).

## 2026-11-13 — Phase 6: edits are spec patches on finished values, re-solved with the edited dimension held
- **Context**: Gate items "0.5 mm thinner changes only that parameter" and "flower slightly bigger keeps the gold target by re-solving the band". The solver's one scale knob multiplies width, thickness and flower/pendant size together, so patching a field and re-solving naively would undo the edit.

(8) Report: changed fields (finished before/after), dimensions the re-solve moved, weight Δ (finished g), price Δ — both versions quoted with `pricing.quote` under one fresh plan (today's RateSource rate) so Δ reflects the design only; exchanges also report `to_pay` Δ. - **Alternatives**: re-solve with no lock (flower edit partly undone, thinner edit fully undone); keep the old scale and let weight drift (breaks the gold-target promise); a per-field scale knob inside `geometry.py` (touches every builder, incl. ones being edited concurrently).

## 2026-11-13 — Phase 4: mesh-based manufacturability checks (meshdfm)
- **Context**: Phase 4 gate (spec §6): checks run on the mesh, rule values in a per-process config, pass/warn/fail with a location into the job card, deliberately bad specs, one relaxed retry. User rule: no fixed gram minimum for new piece types; mesh checks decide what can't be cast and the refusal names the thin part.
- **Decision**:
  1. **Measurement** (`packs/jewellery/meshdfm.py`): area-weighted random points on the gold surface (numpy, fixed seed, `samples_per_mm2` = 6 clamped to 1,500–6,000), each ray-cast inward along the face normal with a `mathutils` BVHTree; hit distance = local thickness (plate → thickness, round wire/claw → diameter, finger-hole face → radial shank thickness). Chains are measured in a 12 mm window at the lowest link (every link is the same wire). Earrings: only `Built.gold` (one earring; the mirror is never measured). Bought findings (butterfly backs, screw backs) are not in the mesh, so not measured.
  2. **Robustness** (all assumed, in `data/dfm_rules.json`): (a) closing: each sample takes the thickest sample within `fill_radius_mm` = 1.25 (a tapering rim or bead edge next to full metal is fed by it; a part thin over > 1.25 mm stays thin). Measured: at 0.75 mm most ellipsoid-petal designs failed even at their balanced scale; at 1.0 the README lotus-pendant order and pendant_temple_lotus at its solved weight failed on petal edges of 0.73–0.75 mm (petals built at exactly 0.8 mm crown thickness taper at the edge); 1.25 passes them while every deliberately thin part (uniform shank, claw, plate, chain wire) still fails. (b) points on a stone seat, and rays that exit into a seat (notched claw tips, seat floors), are not measured: the setter works that metal. (c) a part's value = its 2% low quantile (`robust_quantile`), not the single shortest ray. (d) `measure_tolerance_pct` = 4: a faceted round wire reads d·cos(π/sides) flat to flat (12 sides = 3.4% under), so a reading within 4% under the minimum is a warn, not a fail.
  3. **Rules / parts**: `ring_shank` (finger-hole samples, located by clock position, 12 = top), `prong` (claw settings: the original solitaire ring and `claw_families` ring_three_stone / ring_halo_solitaire; samples within `setting_reach_mm` = 1.2 of the main stone), `setting` (other stone settings), `wall` (the rest, with the family's own minimum via `family_wall`: chains 0.5 mm wire, jhumka 0.6 mm ornament wall; else 0.8 mm), `soft_gold_claws` (claw setting, karat ≥ 22, stone > 5.0 mm → **warn**, assumed: 22K claws bend; suggests bezel / 18K claws / ≥ 1.0 mm claws), `build` (a builder that raised). Grade: fail < min × (1 − tol), warn < min or < min × 1.1, else pass. Minimums: the Phase 3 sourced values (shank 1.5, wall 0.8, prong 0.8, post 0.8, chain wire 0.5, ornament wall 0.6) live in `data/dfm_rules.json`, separate from `data/casting.json` `dfm_min_mm` (the spec-level bounds Phase 3 owns); both hold the same three sourced numbers today. Posts have no separate mesh rule: they are part of `wall` (0.8 mm; jhumka posts are clamped ≥ 0.8 by `_ornament.post_d` but checked at the 0.6 ornament wall) — assumed.
  4. **Where it runs**: `JewelleryPack.solve` = `_solve_core` (the old solve) → `meshdfm.check_spec` at the solved scale (build + check, cached by spec hash + rules). Fail (or a builder exception) → **one retry**: `meshdfm.relax` — a family's `relax` hook (new optional `Family.relax`; ring_floral_cluster drops a petal stone, ring_halo_solitaire drops the shoulder stones), else a generic "less spread-out design": width and motif size × `relax_factor` 0.85, one petal fewer (lotus pendant / floral ring), 15% fewer bangle beads; thickness never reduced. Re-solved to the SAME gold target, the smaller design lands at a larger scale, so thin parts thicken. Still failing (or the re-solve is infeasible) → `Solved(ok=False)` with `binding_constraint = "mesh check: <rule> at <location>: x mm < min mm"`, an explanation naming the thin part and the retry, best achievable and 3 options. A generic "raise the scale floor" retry was rejected: at a fixed gold target the scale is fixed by the weight, so it could never succeed. Edits (`apply_edit`): checked, no relaxed retry (the customer asked for exactly that change) — assumed. `deliver` checks the built mesh when a `Solved` arrives without results.
  5. **Job card**: `Solved` gained `warnings` (warn/fail lines, plus "first mesh check failed …; retried once with …") and `mesh_checks` (`{rule, status, measured_mm, min_mm, location, text, samples}`); `job_card.json` carries `mesh_checks`, the warnings, and passes as `checks_passed` entries `mesh: …`; `job_card.md` has a "Manufacturability (measured on the mesh)" section.
  6. **Cost**: a check is 0.03–1.0 s (big bangles at 6,000 samples ~1 s), plus one build at the solved scale (0.1–3 s). Measured on probe orders: 1–7 s per design including the solve (the 7 s were jhumka, whose build alone is ~1.5 s).
- **Why**: measuring what will actually be cast catches what the spec-level rules miss (measured at balanced scale: three-stone side claws are 0.72 mm by construction; lotus/temple/paisley pendant petals and the butterfly ring's wings run under 0.8 mm), while the closing and seat exclusions stop rims, bead edges and claw notches from failing every design.
- **Alternatives**: voxel thickness map (slower in Python, resolution-limited); shape-diameter cones (overestimate tilted wires); strict minimum ray (every design fails on its rims); per-family part annotations (19 builders to touch; may come later through the same rule config).
- **Known effect**: some catalogue designs (lotus pendant statement, temple/paisley pendants at low scales, butterfly at its statement weight) now come back infeasible at weights where they were solved before, naming the thin part. Builders could clamp those decorative parts to 0.8 mm (catalogue owners).
